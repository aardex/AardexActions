# Reviewed Terraform apply (draft)

This action is an opt-in companion to `terraform-deploy`'s `plan-storage: azure-blob` mode. It applies the previously saved binary; it never generates a new plan. It does **not** configure GitHub Environment protection. Do not use this action unless the consumer job references the correct, already-protected environment and the reviewer can verify the plan ID, SHA-256, commit, workspace and plan summary before approving.

## Contract

1. A trusted dispatch checks out the full plan commit and calls `terraform-deploy` with `apply: 'false'`, storage mode and a target environment. The action hashes the saved binary before the count/human summaries, then checks that hash again before a single conditional Azure Blob upload. The storage mode fails if counts are unavailable or an explicitly requested human-readable summary could not be generated. GitHub may still fail to upload a step summary without failing the job, so the reviewer must verify it is visible. Its `plan-id` and `plan-sha256` outputs and job summary are the independent review record. The identifier contains repository, environment, workflow run, attempt and a random UUID. The blob metadata also records commit, workspace, Terraform root and version, creation time and SHA-256. No binary, JSON plan or captured CLI-output artifact is uploaded to GitHub.
2. An operator opens the plan run, reviews the human-readable summary if permitted, verifies that it was actually rendered, and copies the ID, SHA-256, commit and workspace from that same run. For counts-only or an oversized/failed rendering, the summary does **not** show full changes; use an approved review process or do not apply. A separate local re-plan is not a review of the same saved plan.
3. A separately dispatched apply job must reference the protected environment. The reviewer independently compares its dispatch inputs with the reviewed plan run before approving. A job protection rule is the authorization control; an action cannot create or guarantee it. As defense in depth, the action checks the current run's review history and environment configuration, and fails if required-reviewer evidence, no self-review, disabled admin bypass or a branch policy is missing. It rejects rerun attempts because the GitHub review-history API is run-scoped. This check is not a substitute for a correctly protected job, restricted OIDC trust and an independent human review. The target repository needs a GitHub plan supporting private-environment required reviewers and `actions: read` plus `id-token: write` on the job.
4. The consumer checks out the supplied commit; the action verifies it, initializes Terraform with the existing deployment identity, selects the existing workspace and verifies its name and Terraform version. It uses the separately federated plan-reader identity to fetch metadata and binary via Private Link, validates repository, environment, commit, root, workspace, version, run/attempt, service timestamps and the separately supplied SHA-256, then atomically creates a claim blob with `If-None-Match: *`. Expiry is seven days measured using the Blob service response date and blob last-modified time. The runner clock must be within two minutes of the service; a conservative deadline is checked again immediately before apply. It rechecks the local SHA-256 immediately before invoking `terraform apply` with **that file**, using the original deployment identity. Storage OIDC uses a separate Azure CLI configuration and does not replace the deployment login; no re-plan occurs.
5. A successful or failed apply gets a create-only result record when possible. A claim remains after failure, cancellation, runner loss or result-record failure, and blocks all later automatic attempts. Investigate target and state: apply may have partially succeeded. Obtain fresh authorization, generate a **new** plan and get a new review; never delete a claim to retry. Terraform's normal remote-state lock remains enabled. Use the same consumer `concurrency` group for plan and apply; it does not coordinate other repositories or manual operators, and GitHub can replace an already-pending run.

The plan-store principal has plan-read plus claim/result-create permissions. The plan publisher can create plan blobs but not read, modify or delete them. Azure RBAC is additive: the required immutability property only holds if neither workload identity has broader inherited data/control-plane rights and no trusted administrator changes those rights. The current shared deployment principal has broad administrative authority, so this must be separately reviewed; the create-only storage identities prevent ordinary plan/apply jobs from changing blobs only within the intended boundary. The storage roles are container-wide, not scoped to a repository/environment prefix; the proposed account is only for Persistence Alpha. Do not expand it to other consumers without separate container/identity scoping and review. Conditional creation and SHA verification do not protect against a compromised authorized plan producer, a compromised runner, an administrator changing storage policy, or a reviewer approving mismatched inputs. The supplied SHA must come from the trusted original plan run, not the downloaded blob itself. Result or plan cleanup must never be used to authorize a replay.

A single upload is limited to 32 MiB because the create-only Azure role cannot stage multipart blocks. The plan and metadata remain in a private container; an additional private events container holds claims/results. Repository, environment, workspace and root identifiers must use the safe path characters accepted by the action; unsupported names fail closed. The action rejects unknown context, missing files, expired or mismatched plans, checksum failure, duplicate claims and failed uploads; no fallback to an unpersisted/new plan is permitted. An interrupted job may leave a local plan file or no result record; persistent runners need restricted access and cleanup. Lifecycle deletion is asynchronous, and a role change by an Azure administrator can invalidate assumptions.

See [plan storage infrastructure](https://github.com/aardex/TerraformInfrastructure) for the separately reviewed Terraform root and bootstrap, and [Persistence Alpha plan](../terraform-deploy/examples/persistence-alpha-plan.yml) / [apply](../terraform-deploy/examples/persistence-alpha-apply.yml) reference workflows. They are documentation examples only, not active workflows. Replace `ACTION_COMMIT` with the reviewed immutable AardexActions commit; configure the same Terraform root, provider lock file, state backend and input sources for both runs. Provider/module dependencies must be available at apply and match the plan; Terraform may reject a stale plan after state changes. The examples require a separately scoped `TF_MODULES_READ_TOKEN` for private modules instead of the current broad `PAT_TOKEN`; coordinate its provisioning and module access with INFRA-423. Do not pass privileged tokens to untrusted PR code.

## Human-readable summary risk

Terraform redacts only values it recognizes as sensitive. Unmarked or transformed secrets, addresses, output values and other identifiers can appear in the human-readable summary. GitHub's automatic secret masking is not guaranteed. A private repository is not a per-plan confidentiality boundary: use human-readable mode only if every run viewer and integration is authorized for the plan, and inspect the summary before approval. GitHub limits each step summary to 1 MiB; this action omits text over 180000 bytes and retains counts when possible. If sensitive information is published, follow incident procedures, delete the affected workflow run and rotate exposed credentials as appropriate.

## Validation and outstanding gates

Offline tests use synthetic plan bytes, an in-memory Blob model and fake Terraform; they do not contact Azure or execute real apply. In `terraform-deploy/tests`, run `python3 -m unittest test_plan.PlanTests test_plan.LocalTerraformTests.test_real_human_plan_sensitive_and_nonsensitive test_plan_store test_approval -v`. The separately existing `test_disposable_local_plan_and_apply` performs a real Terraform apply to a temporary local state and is **not included** in that command. Run `python3 -m py_compile` for the two Python helpers, `bash -n` on shell scripts and `git diff --check`.

The Azure create-only RBAC, conditional requests, private DNS/routing, lifecycle deletion and GitHub approval-history behavior are not verified against real services by these tests. Required reviewers are currently absent on Persistence Alpha. Do not merge or activate until the owners resolve these gates and perform an explicitly authorized nonproduction smoke test using synthetic inputs. Exact-plan replay/recovery, rollback, historical plan artifacts and shared runner hygiene also need owner review.
