# Deployment and release mechanics

This repository distributes composite actions through Git refs (`aardex/AardexActions/<action>@<ref>`). It has no repository-wide publication/build workflow or deployment manifest. The only committed workflow is a PR-opened Copilot comment example. A consumer controls triggers, approvals, runner permissions and target environments; a `uses:` reference alone does not deploy anything. `@main` is mutable and internal calls to `@main` are not coupled to a caller's pinned ref. Verify all transitive action refs before adopting or releasing changes.

| Family | Observable behavior in `action.yml` |
| --- | --- |
| Terraform deploy/destroy | Both initialize, validate and plan with Terraform 1.13.3; default `apply: 'false'`. With `apply: 'true'`, they apply the saved plan with `-auto-approve`. **No manual approval step is implemented** in either action. Deploy declares `needs-approval` but never uses it; any approval must be enforced by the consumer workflow/environment. Destroy uses a destroy plan; check target, workspace and artifact before any opt-in apply. |
| Terraform format/docs | Format-validate defaults to `fix: 'true'` and `auto-commit: 'auto'`, which can commit and push formatting changes; set `fix: 'false'` and `auto-commit: 'false'` for a read-only check. `terraform-docs` generates README content and uploads an artifact; `terraform-docs-index` writes an index to a target README. |
| Azure apps/images | App Service and Function actions build/test and deploy to Azure via publish profile. Java action builds/tests and deploys a WAR. Container App action publishes an image, scans with Trivy unless `skip-check: 'true'`, then updates the Azure Container App. Image publishing pushes version and `latest` tags to ACR, with a registry build cache. Target naming and registry access come from consumer inputs. |
| Packages and GitHub | NuGet publish actions pack/push to GitHub Packages; release/RC/versioned variants also run build/test, whereas alpha only packs. `dotnet-component-release` updates a consumer version, calls the commit/push action and then the tag/release action. `github-create-tag-release` invokes `softprops/action-gh-release@v2` with tag `v<version>` and a minimal generated body. `github-commit-push` and `commit-version-changes` can push to the consumer repository. |

Before any real deployment or release, review the **selected revision** of the action and consumer workflow, verify target subscription/resource, permissions, plan/artifacts and change approval with the consumer's authority. This documentation does not grant permission to publish or apply. There is no evidence here of a standard staging-to-production path, rollback procedure, repository release approver or release cadence; those require an owner-approved workflow or external operational authority. GitHub Releases created by the helper action are for whichever repository invokes it, **not evidence that this action library uses GitHub Releases as its own history**. See [CHANGELOG](../CHANGELOG.md) for the recorded library history and its limits, and [operations](operations.md) for available diagnostics.
